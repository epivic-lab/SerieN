## Confini di fiducia e capacità raccomandata

GitHub Pages serve codice pubblico, scaricabile e modificabile dall'attaccante: nessun segreto condiviso può autorizzare un workspace dal bundle. WorkspaceId, project URL, hash e anon/publishable key non sono capacità di accesso. Il client parla soltanto a un gateway HTTPS futuro che verifica ogni richiesta; il gateway accede al DB con un ruolo server dedicato a privilegi minimi. I dati di autorizzazione/capacità vivono in schema privato non esposto. Nessuna credenziale privilegiata, capacità reale, invito o recovery secret nei documenti, URL permanenti, log o repository.

**Scelta proposta:** una coppia di chiavi ECDSA P-256 per dispositivo, privata non esportabile WebCrypto in IndexedDB; il server registra chiave pubblica, workspace, deviceId, scope, epoch e stato revocato. Capacità = binding autorizzato di quella chiave al workspace; conoscere ID e public key non basta. Si evitano bearer token durevoli nel localStorage. La chiave non esportabile limita l'esfiltrazione, **non impedisce che un XSS firmi richieste mentre è attivo**. Se il browser non conserva CryptoKey in modo affidabile, fallire pairing cloud con messaggio esplicito, senza retrocedere a un token in chiaro. Backup del DTO non contiene chiavi; export recovery separato.

Ogni richiesta firmata include versione protocollo, keyId/deviceId, epoch, operation, workspaceId, layoutId, metodo, path canonico, SHA-256 body, request_id, nonce casuale 128 bit e issuedAt; encoding canonico versionato con dominio `SerieN-capability-v1` e audience URL esatto del gateway. Gateway ammette clock skew massimo ±120s e memorizza nonce usati per 5 minuti. Nessun redirect autorizzato con riuso firma; digest e path sono verificati sul contenuto effettivo, non su header client fidati. Operazioni di sola lettura sono firmate anch'esse. Retry produce nuova firma/nonce/timestamp ma **stesso request_id e medesimo envelope**: replay di trasporto è negato, retry applicativo restituisce ricevuta. CORS da solo non autorizza niente.

### Attivazione, pairing e recovery senza account

1. **Primo dispositivo:** un operatore autorizzato usa un canale amministrativo separato (mai il sito pubblico) per creare workspace e invito one-time casuale 256 bit con scope massimo owner, scadenza 10 minuti, hash/HMAC server del segreto e stato pending. Nessun endpoint di creazione workspace anonimo. L'operatore e il destinatario verificano fuori banda il fingerprint della chiave pubblica candidata prima dell'approvazione. Il browser comunica public key, invito e prova di possesso; consumo invito + device binding + epoch iniziale avvengono atomicamente. Nessun dispositivo autorizzato dal solo possesso di workspaceId.
2. **Altro dispositivo con uno attivo:** il nuovo browser crea chiave e fingerprint, riceve dal server una challenge pending a vita breve (rate-limited, nessun dato workspace restituito). L'owner attivo autorizza esplicitamente fingerprint, workspace e scope della challenge firmando. Consumo challenge atomico, bound a quella chiave, non riscattabile con una chiave sostituita. Invite scade in 10 minuti, un solo redeem. Scope reader/editor non può diventare owner o creare altri inviti. Nessuna condivisione automatica della chiave privata.
3. **Kit recovery:** al primo pairing confermato l'owner genera un recovery secret casuale 256 bit e salva il kit offline fuori dal browser con workspaceId e versione recovery; al server solo verifier HMAC con pepper server, nessun segreto recuperabile. Il kit consente di registrare una nuova chiave con prova di possesso. Consumo del verifier + registrazione + revoca di tutti i vecchi device/inviti + incremento recovery epoch sono un'unica transazione. Dopo successo si emette un nuovo kit; il vecchio è inutilizzabile. Mostrare e far confermare la conservazione del kit prima di considerare conclusa l'attivazione; no recupero mediante email/nome/dispositivo presunto.
4. **Perdita completa:** se non restano device owner né kit valido, il cloud non è recuperabile automaticamente. L'operatore può revocare per contenere il danno ma non riassegnare dati sulla base del solo nome. Un eventuale recupero amministrativo richiede un protocollo distinto di prova di possesso approvato dalla Regia; non è una backdoor implicita. Il kit è una capacità potente: chi lo ruba può prendere il workspace e revocare altri device.

Inviti/recovery trasmessi soltanto via POST TLS dal form di attivazione, mai query string, analytics o clipboard automatica. Se si adotta in futuro un link/QR, il segreto deve stare nel fragment, essere rimosso immediatamente con replaceState e non essere caricato da terzi; questa variante richiede test specifici e non è il default. Risposte pairing non enumeranti, rate limit globale/per invito/IP, confronti verifier constant-time e audit senza valori dei segreti.

**Revoca:** owner può revocare device, inviti e recovery version, impedendo ogni nuova operazione dopo il commit; anche il device revocato non può leggere ricevute. Autorizzazione e revoca si sincronizzano sulla stessa riga lock: save già autorizzato e completato prima della revoca resta durevole, save arrivato dopo è negato. Revoca non annulla dati già scaricati né un checkpoint legittimamente committato prima del lock. JWT/cache di autorizzazione lunghi non soddisfano questa garanzia.

**Rotazione chiave:** owner/device autorizzato registra nuova public key con firma della vecchia e prova della nuova; due fasi prepare/confirm a vita breve, nessun cutover prima dell'ack persistito dal nuovo device. Confirm atomico incrementa epoch e revoca vecchia chiave. Ack perso: nuova chiave può leggere esito della propria rotazione con challenge dedicata; nessuna riattivazione della vecchia. Kit recovery consente uscita da perdita di entrambe. Rotazione del pepper/verifier richiede mantenere versione per kit attivi o reemettere kit con conferma owner, non invalidarli silenziosamente.

### Matrice di autorizzazione esplicita

Scope legati a workspace, mai auto-dichiarati nel body. Owner non è un ruolo DB/superuser; è uno scope applicativo. Anche letture e storico richiedono autorizzazione.

| Operazione | Pubblico non paired | reader | editor | owner | Operatore amministrativo |
|---|---|---|---|---|---|
| Asset statici CC0 già pubblici e bundle | sì | sì | sì | sì | sì |
| Head/snapshot/storico/ricevute/catalogo del proprio workspace | no | sì | sì | sì | nessuna lettura ordinaria; break-glass separato/audit |
| Save CAS e recovery da vecchia revisione | no | no | sì | sì | no nel percorso applicativo |
| Creare workspace e primo invito | no | no | no | no | sì, canale separato |
| Creare/approvare pairing per altri device | no | no | no | sì, scope esplicito | solo bootstrap o procedura separatamente approvata |
| Revocare altri device/inviti, sostituire kit recovery | no | no | no | sì | revoca emergenza autorizzata e audit |
| Ruotare la propria chiave senza elevare scope | no | sì | sì | sì | no |
| Redeem invito / kit valido + prova chiave | solo protocollo limitato, nessun dato finché non verificato | come pubblico | come pubblico | come pubblico | no bypass |
| Leggere/scrivere altro workspace o mutare topologia/catalogo globale | no | no | no | no | solo workflow distinto; mai tramite Save |
| Migrazioni/RLS/grants/deploy/secrets | no | no | no | no | processo amministrativo separato e autorizzazione specifica |

Non è prevista cancellazione definitiva dei checkpoint nella v1. Nessuno scope applicativo concede DELETE raw o SQL arbitrario.

## Threat model specifico

| Minaccia / percorso | Controlli proposti e oracolo | Rischio residuo |
|---|---|---|
| Bundle Pages pubblico, credenziale incorporata | Nessun segreto browser condiviso; gateway prova chiave + scope; Data API negata. Un client ricompilato senza capacità ottiene zero dati | Codice e asset pubblici restano copiabili |
| Furto dispositivo/capacità, perdita IndexedDB | Chiave non esportabile, device list/revoca, rotazione, kit offline; nessuna lettura dopo revoca | Malware/sistema sbloccato può firmare; perdita totale senza kit irrecuperabile |
| Pairing di un attaccante o recovery sostituito | Fingerprint approvato, binding alla nuova public key, proof of possession, consumo one-time, TTL e scope | Canale fuori banda compromesso o kit rubato trasferisce autorità |
| XSS / dipendenza compromessa / backup malevolo | Solo testo per nomi; schema chiuso e allowlist asset; no HTML dal payload; CSP compatibile Pages tramite meta, script/self e connect-src gateway esatto, no script terzi; niente eval | XSS nello stesso origin può usare CryptoKey. CSP definitiva richiede audit inline/importmap esistenti prima di applicarla; nessuna modifica CSP fatta qui |
| Replay, firma contraffatta, CSRF | Firma domain-separated con metodo/path/body/epoch, nonce e skew; no cookie bearer implicito; CORS Origin esatto e Referrer-Policy no-referrer via meta dove supportato | CORS/Origin falsificabili fuori browser: firma resta necessaria; rate limit prima della verifica costosa |
| BOLA / IDOR cross-workspace | Binding server workspace/device, confronto URL/body/DTO; FK composite e RLS USING/WITH CHECK; errori non enumeranti | Gateway compromesso può usare i privilegi concessi; limitare ruolo e audit |
| Concorrenza save/recover/revoke | Lock autorizzazione→head, CAS, ricevuta unica, snapshot immutabile, revoca linearizzata | Nessun merge automatico; conflitto richiede scelta esplicita |
| DoS, quota, payload enorme, crypto flooding | Limite 2MiB prima parse, array limiti, timeout/statement_timeout, rate e storage budget per workspace/device/IP, backoff; transazione breve e indici workspace | DoS di rete/hosting non eliminabile. Budget numerici di richieste/storage da dimensionare in 6A.2 con quote reali: finché non fissati gateway non abilitabile |
| Privilegi server→DB | Ruolo worker dedicato NOBYPASSRLS (NOLOGIN se assunto tramite un login server separato), non proprietario delle tabelle, permessi solo necessari, connessioni server e TLS; funzioni invoker in schema privato, search_path fisso; nessun SQL client | Furto credenziale gateway o bug di contesto può compromettere gli scope del ruolo; segregare amministrazione/secrets, audit e rotazione |
| DB service key o view che bypassa RLS | Preferire ruolo dedicato senza bypass; nessuna service_role nel client. View security_invoker, niente funzioni definer pubbliche o EXECUTE PUBLIC | RLS non protegge da superuser/bypassrls; una service_role server eventuale richiederebbe nuova giustificazione e audit, non è la scelta raccomandata |
| Asset URL da backup, geometria non approvata | Manifest server pinning digest/revisione; nessun fetch di URI arbitrari, archivi o path traversal; solo Kenney approvati e native builder | Asset indisponibile lascia freeze; niente fallback che cambi ingombri |
| Tampering journal/backup | Hash verifica integrità, validazione completa; ricevuta server distingue checkpoint confermato | Hash non autentica l'autore. Un dispositivo autorizzato può proporre stati diversi entro vincoli; non è anti-cheat |

Non si promette riservatezza end-to-end: il server vede il DTO. Log solo request_id, device pseudonimo, esito e revisioni; niente body, segreti o firme riutilizzabili. Retention/quotas, monitoraggio e capacità dell'operatore vanno approvati prima dell'abilitazione del gateway. 5E rimane audit complessivo successivo, queste difese non sono rinviate.

## Alternative realistiche di ownership

| Alternativa | Compatibilità senza login | Vantaggi | Costi e rischi |
|---|---|---|---|
| A: workspace esplicito + device capabilities, gateway con ruolo DB limitato | Completa; nessuna identità Auth cliente | Owner è il workspace durevole, revoca per device, separazione inventario/dispositivo, nessuna credenziale Auth nel browser | Nuove strutture workspace e migrazione FK/RLS; pairing/recovery da collaudare; contesto transazione affidato al gateway |
| B: Auth user tecnico «shadow» per workspace, conservando owner_id | Possibile con account creato solo dal server, gateway capability davanti; nessun login UI | Riusa FK auth.users e molte policy uid; JWT server scoped a un singolo user può limitare il DB | Dipendenza da lifecycle Auth/server; cancellazione user cascada dati; revoca JWT non immediata senza verifica device; non confondere anonymous sign-in pubblico con autorizzazione workspace |

**Raccomandata A.** Rende D04 esplicita e non trasforma un dispositivo o un account Auth nascosto nel proprietario dei dati. B resta realistica ma non comporta autorizzazione a creare utenti né a distribuire JWT browser in 6A.1. Un anonymous sign-in aperto da solo non risolve ownership/pairing: chiunque otterrebbe authenticated e policy troppo ampie sarebbero pericolose. Nessuna anon write o policy permissiva proposta.

Per A: RLS conserva isolamento per workspace con predicato membership/device attivo e scope, contesto impostato **solo dal gateway**, transaction-local, mai dal body o da una variabile browser. Ruolo worker non può modificare registry capacità o catalogo. Read path invoker con contesto verificato; update sempre USING e WITH CHECK. `SET LOCAL`/GUC non è prova crittografica: un ruolo DB compromesso può impostare altro contesto. La protezione è il gateway autenticato + ruolo limitato + FK/RLS; la compromissione del gateway è dichiarata nel threat model. Una versione con token server firmati e ruolo per workspace può migliorare separazione ma richiede altro progetto/review, non è necessaria al contratto attuale. Nessun endpoint consente SQL o SET dal client. Pooling deve azzerare contesto al termine della transazione; test dedicato di riuso connessione fra due workspace.

### Nuove strutture minime e percorso di migrazione proposto

Nessuna nuova migration file creata. Il lavoro futuro richiede autorizzazione distinta e verifica schema immediatamente prima di applicarlo.

1. Registry privato: `workspaces(id, status, auth_epoch)`, `workspace_devices(id,workspace_id,public_key,scope,key_epoch,revoked_at)`, inviti/challenge one-time con verifier/expiry/approved_key, recovery verifier versionato, nonce replay TTL. PK/FK e unique(workspace,id). Nessun segreto in chiaro; verifier e public key non presenti nel DTO. Tabelle RLS attiva, zero grant browser. Ruolo pairing separato dal worker snapshot; solo procedura di autorizzazione può mutare registry. Una tabella privata workspace_device_locks separata dal registry coordina save/revoca: il worker può bloccare/aggiornare solo il marker della propria operazione, senza modificare scope/chiavi/revoche; il percorso pairing/revoca prende lo stesso lock prima di mutare registry. Un head per layout, con workspaceId, revision bigint, snapshotId e digest; FK composta assicura stesso workspace/layout. Head e receipt creati nello stesso contratto transazionale.
2. Aggiunta nullable `workspace_id` sulle tabelle owner-scoped (tutte eccetto stock_models e layout_segments); backfill controllato tramite mapping `legacy owner→workspace` approvato, senza assumere che un chiamante possegga i dati legacy. Qui i conteggi sono zero ma vanno ricontrollati prima della migrazione. Aggiungere unique composite e FK workspace per tutte le relazioni; prevenire assegnazioni tra workspace anche se UUID validi. Indici workspace/FK, head/layout revision e deduplica; no indice JSON universale senza query dimostrata.
3. Durante transizione, preservare owner_id e FK legacy per dati esistenti. Dopo dual validation, le nuove righe workspace usano owner_id nullable e workspace_id obbligatorio; eliminare default auth.uid e NOT NULL owner solo al cutover approvato. Aggiungere CHECK di modalità: legacy owner non nullo/workspace nullo oppure workspace non nullo/legacy owner eventualmente conservato per backfill verificato; nessuna riga senza proprietario. Escludere nuove scritture legacy nel worker. Aggiornare trigger e FK/policy a workspace prima di ammettere dati nuovi, mai temporanee policy true/anon. L'eventuale rimozione definitiva di owner_id è fase successiva, non requisito per il primo cutover.
4. Aggiungere Journey/revision a loose placements, stock_model_versions immutabile per la storia dei manifest e valori train/motion negli spazi JSON già disponibili, digest/provenance a snapshot, deduplica workspace a receipts, head. Per inventario storage garantire esclusività anche rispetto membership/loose; settings non la garantisce da solo: validatore e vincolo/trigger transazionale devono controllare l'assegnazione sotto lock stock_item. Aggiornare check_snapshot senza perdere otto interruttori/hash/STOPPED; check_ready e ordine loco+carri restano. Nessun limite DB corrente al numero totale carri/treni: i limiti D06 devono essere aggiunti al commit validator.
5. Negare DML diretto browser e scrittura del catalogo al worker; policy SELECT per lettura e USING/WITH CHECK per update/insert scope. Definire invoker transaction API privata per snapshot/proiezioni/head/receipt, senza EXECUTE PUBLIC o SECURITY DEFINER come scorciatoia. Solo il ruolo server autorizzato la può chiamare; setup connessione/contesto non è una API browser. Verificare grant/Default Privileges e esposizione schema reale, incluse view e nuove funzioni. Nessun `user_metadata` in decisioni autorizzative.

**Rollback/preservazione:** prima di ogni cambio catturare DDL/versioni, conteggi e backup verificato; rehearsal su ambiente isolato autorizzato. Migrazione iniziale additiva, vecchie colonne/snapshot conservati e confronto proiezioni prima cutover. In errore prima cutover, disabilitare nuova write path e restare sul modello precedente; non svuotare tabelle. Dopo nuove scritture con owner_id nullo non si può riattivare alla cieca il vecchio schema Auth: mantenere lettura congelata/esportazione e applicare forward fix o restore controllato del backup senza perdere checkpoint successivi. Non inventare Auth users per consentire rollback. Eventuale dual-write con schema legacy richiede protocollo aggiuntivo: non viene assunto. Disabilitare gateway ferma nuove scritture, non revoca la durabilità dei checkpoint confermati.

## Gate sicurezza prima dell'implementazione

La raccomandazione A, il protocollo pairing/recovery e la matrice richiedono approvazione della Regia. Prima di abilitare cloud: fissare budget reali quote/rate, verificare disponibilità CryptoKey su browser target e hosting gateway/TLS, prove P08–P12/P16/P17, pool-context isolation, privilegi effettivi e configurazione Data API, CSP compatibile con il sito esistente e piano backup/restore. Nessuno di questi test futuri è marcato PASS qui. L'esito della 6A.1 riguarda la coerenza documentale e le osservazioni correnti, non la sicurezza di un gateway ancora inesistente.
